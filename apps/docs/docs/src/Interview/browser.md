# 浏览器相关

## 五层网络模型

1. 物理层（Physical Layer）：
   - 物理层是网络模型的最底层，负责传输比特流（bitstream）通过物理介质进行通信。
   - 它定义了传输介质的电气特性、物理连接的接口、数据传输速率和数据编码等。
2. 数据链路层（Data Link Layer）：
   - 数据链路层建立在物理层之上，提供可靠的点对点数据传输，通过帧（frame）进行通信。
   - 它处理帧的封装、帧同步、差错检测和纠错等功能，确保数据的可靠传输。
3. 网络层（Network Layer）：
   - 网络层负责将数据分组（packet）从源节点传输到目标节点，通过路由选择和转发进行通信。
   - 它定义了网络中的逻辑拓扑结构、数据包的寻址和路由选择算法等。
4. 传输层（Transport Layer）：
   - 传输层提供端到端的数据传输服务，负责数据的分段和重组，通过端口号进行通信。
   - 它提供可靠的数据传输、流量控制、拥塞控制和错误恢复等功能，如 TCP 协议和 UDP 协议。
5. 应用层（Application Layer）：
   - 应用层是最顶层的层次，提供应用程序之间的通信服务，通过特定的应用协议进行通信。
   - 它包括各种网络应用协议，如 HTTP、FTP、SMTP 和 DNS 等，用于实现特定的网络应用功能。

## TCP为什么是3次握手，4次挥手？

**3次握手：**

TCP是一个双工协议，为了让双方都保证，建立连接的时候，连接双方都需要向对方发送SYC(同步请求)和ACK(响应)，握手阶段双方都没有繁琐的工作，因此一方向另一方发起同步(SYN)之后啊，另一方可以将自己的ACK和SYN打包作为一条消息回复，因此是3次握手——即需要3次数据传输。

**4次挥手：**

到了挥手阶段，双方都有可能有未完成的工作。接收到挥手请求的一方，必须马上响应(ACK)，表示接收到了挥手请求。最后等所有工作结束，再发送请求中断连接(FIN)，因此是4次挥手。

<br>

## TCP和UDP区别

相同点：都位于网络模型的传输层

不同点：

- TCP 提供可靠的、面向连接的传输，适用于需要可靠传输、顺序性和重传机制的应用，如网页浏览、文件传输、电子邮件等
- UDP 提供无连接的、不可靠的传输，适用于实时性要求高、对数据完整性要求相对较低的应用，如音视频传输、实时游戏等

<br>

## TCP为什么不一次发送完所有的数据？

- 为了稳定性，一次发送的数据越多，出错的概率越大
- 为了效率，拆分数据包就能更好的利用这些并行的路径
- 发送和接收数据的时候，都存在着缓冲区
- 在传输层封包不能太大，以缓冲区大小为单位
  - TCP协议：会将数据拆封成不超过缓冲区大小的一个个部分
  - 每个部分有称为TCP段(TCP Segment)

<br>

## TCP Header中的MSS是什么？

- 是TCP Header中的可选项
- 可选项控制TCP段的大小，涉及发送、接收缓冲区的大小设置，是一个协商字段

<br>

## TCP拆包和粘包的作用是什么？

拆包：将数据拆封成多个TCP段传输，将任务拆分处理，降低整体任务出错的概率，以及减小底层网络处理的压力

粘包：为避免数据过小造成资源浪费，将多个数据合并成一个TCP段发送

**需要保证数据经过网络的传输，又能恢复到原始的顺序，TCP利用(Seq, Ack)的唯一性来确定分包之间的顺序关系**

<br>

## 滑动窗口和流速控制是什么？

滑动窗口是TCP协议控制可靠性的核心，发送方将数据拆包，变成多个分组(即TCP段)，然后将数据放入一个拥有滑动窗口的数组，依次发出，仍然遵循先入先出(FIFO)的顺序，但是窗口中的分组会一次性发送。窗口中序号最小的分组如果收到ACK，窗口就会发生滑动，如果最小序号的分组长时间没有收到ACK，就会触发整个窗口的数据重新发送。

<br>

## 什么是Tunnel技术？

两个网络，用隧道连接，位于两个网络中的设备通信，都可以使用这个隧道。如果两个IPv6网络被IPv4分隔开，那么两个IPv6网络的出口处就可以用程序实现一个隧道。

<br>

## 127.0.0.1, localhost, 0.0.0.0 有什么不同

`127.0.0.1` 是本地回环地址（loopback），发送到 loopback 的数据会被转发到本地应用。
`localhost` 指代的是本地计算机，用于访问绑定在 loopback 上的服务。`localhost` 是一个主机名，不仅仅可以指向 IPv4 的本地回环地址，也可以指向 IPv6 的本地回环地址 [::1]。
`0.0.0.0` 是一个特殊目的 IP 地址，称作不可路由 IP 地址，它的用途会被特殊规定。通常情况下，当我们把一个服务绑定到 `0.0.0.0`，相当于把服务绑定到任意的 IP 地址。比如一台服务器上有多个网卡，不同网卡连接不同的网络，如果服务绑定到 `0.0.0.0` 就可以保证服务在多个 IP 地址上都可以用。

<br>

## NAT是如何工作的？

- NAT解决的是内外网通信的问题，通常发生在内网和外网衔接的路由器中，由路由器中的NAT模块提供网络地址转换能力
- NAT最核心的能力是能够将内网中某个IP地址映射到外网IP，再把数据发送给外网的服务器

## CNAME记录的作用是什么？

CNAME是一种DNS记录，用于将一个域名映射到另一个域名。域名解析的时候，如果看到CNAME记录，则会从映射目标重新开始查询

## HTTP版本差异

1. HTTP/1.0：
   - HTTP/1.0 是最早的 HTTP 版本，于1996年发布
   - 使用短连接，即每个请求和响应都需要建立和关闭一个连接
   - 不支持持久连接（Keep-Alive），每次请求都需要重新建立连接
   - 不支持管道化（Pipelining），即不能同时发送多个请求，需要等待上一个请求的响应后才能发送下一个请求
2. HTTP/1.1：
   - HTTP/1.1 在1999年发布，是目前最广泛使用的版本
   - 引入了持久连接（Keep-Alive），允许多个请求和响应在同一个连接上复用，减少了连接建立的开销
   - 引入了管道化（Pipelining），允许同时发送多个请求，提高了并发性能
   - 支持分块传输编码（Chunked Transfer Encoding），允许服务器逐步发送响应数据，提高传输效率
   - 引入了新的缓存机制，如强缓存和协商缓存等
3. HTTP/2：
   - HTTP/2 在2015年发布，是对 HTTP/1.1 的重大改进
   - 使用二进制协议而不是文本协议，提高了解析效率
   - 引入了头部压缩（Header Compression），减少了头部大小，降低了网络传输消耗
   - 支持多路复用（Multiplexing），允许在同一个连接上并发发送多个请求和响应，提高了并发性能
   - 支持服务器推送（Server Push），服务器可以在客户端请求前主动将资源推送给客户端
   - 具备更好的流量控制和优先级控制机制
4. HTTP/3：
   - HTTP/3 是基于 UDP 协议的版本，使用了 QUIC（Quick UDP Internet Connections）传输协议。
   - 引入了新的传输层协议，提供更低的延迟和更高的性能
   - 支持无连接的多路复用，更加适应现代网络环境
   - 具备更好的拥塞控制和错误恢复机制

HTTP/2 和 HTTP/3 的改进主要关注性能优化和更好的网络适应性，以提供更快、更可靠的网络传输体验。

## HTTP和HTTPS的区别

1. 安全性：
   - HTTP 是明文传输的协议，数据在传输过程中不加密，容易被窃听和篡改
   - HTTPS 使用 `SSL/TLS` 加密协议对通信内容进行加密，确保数据的机密性和完整性，提供更高的安全性
2. 传输方式：
   - HTTP 使用标准的 TCP/IP 传输方式，默认使用端口号 80 进行通信
   - HTTPS 在 HTTP 的基础上添加了 `SSL/TLS` 加密层，使用加密的 TCP/IP 连接，默认使用端口号 443 进行通信

在 HTTPS 中，浏览器会验证服务器证书的合法性，包括证书的颁发机构和有效期等。

<br />

## HTTPS握手流程？

1. 客户端向服务器发送一个 **Client Hello** 消息，包含以下信息：
   - 支持的 TLS 版本（如 TLS 1.2、TLS 1.3）。
   - 客户端支持的加密套件（Cipher Suites）。
   - 客户端生成的随机数（Client Random），用于后续密钥生成。
   - 其他扩展信息（如支持的签名算法）。
2. 服务器收到 **Client Hello** 后，回复一个 **Server Hello** 消息，包含以下信息：
   - 服务器选择的 TLS 版本。
   - 服务器选择的加密套件。
   - 服务器生成的随机数（Server Random），用于后续密钥生成。
   - 服务器的数字证书（包含公钥）。
   - 如果需要，服务器会请求客户端证书（双向认证）。
3. **服务器发送证书（Server Certificate）**
   - 服务器将自己的数字证书发送给客户端。
     - 证书包含服务器的公钥、域名、有效期等信息，并由受信任的证书颁发机构（CA）签名。
   - 客户端会验证证书的有效性：
     - 检查证书是否在有效期内。
     - 检查证书是否由受信任的 CA 签发。
     - 检查证书中的域名是否与访问的域名匹配。
4. **密钥交换（Key Exchange）**
   - 服务器发送 **Server Key Exchange** 消息（如果需要），包含用于密钥交换的参数。
   - 根据加密套件的不同，密钥交换的方式可能包括：
     - **RSA**：客户端使用服务器的公钥加密一个预主密钥（Pre-Master Secret）并发送给服务器。
     - **Diffie-Hellman (DH)**：客户端和服务器通过 DH 算法协商出一个共享密钥。
5. 服务器发送 **Server Hello Done** 消息，表示服务器部分的握手已完成
6. **客户端验证并生成密钥**
   - 客户端验证服务器的证书后，生成一个 **Pre-Master Secret**，并使用服务器的公钥加密后发送给服务器。
   - 客户端和服务器使用 **Client Random**、**Server Random** 和 **Pre-Master Secret** 生成相同的 **Master Secret**。
   - **Master Secret** 用于生成对称加密的会话密钥（Session Keys），用于后续的数据加密和解密。
7. **客户端发送完成消息（Client Finished）**
   - 客户端发送一个 **Finished** 消息，包含之前所有握手消息的哈希值，并使用会话密钥加密。
   - 服务器解密并验证该消息，确保握手过程未被篡改。
8. **服务器发送完成消息（Server Finished）**
   - 服务器发送一个 **Finished** 消息，同样包含之前所有握手消息的哈希值，并使用会话密钥加密。
   - 客户端解密并验证该消息。
9. **安全通信建立**
   - 握手完成后，客户端和服务器使用协商好的对称密钥进行加密通信。
   - 后续的所有数据传输都通过对称加密算法（如 AES）进行加密和解密。

<br />

## HTTPS公钥密钥发送了几次请求

1. 在建立 HTTPS 连接时，涉及到的公钥和密钥交换涉及两次请求。这是因为 HTTPS 采用了非对称加密和对称加密相结合的方式来确保通信的安全性

   1. 第一次请求：
      - 客户端发送一个初始的 HTTP 请求到服务器，并提出建立 HTTPS 连接的要求
      - 服务器会将自己的公钥（证书）发送给客户端作为响应
   2. 第二次请求：
      - 客户端收到服务器的证书后，会验证证书的合法性和有效性，包括验证证书的签名和有效期等
      - 客户端还会检查证书中的域名和当前访问的域名是否匹配，以防止中间人攻击
      - 如果证书验证通过，客户端会生成一个用于对称加密的随机密钥（称为会话密钥或对称密钥）
      - 然后，客户端使用服务器的公钥对该随机密钥进行加密，发送给服务器

   通过这两次请求，实现了公钥和密钥的交换：

   - 服务器将公钥发送给客户端，确保客户端可以安全地加密会话密钥
   - 客户端生成会话密钥并使用服务器的公钥进行加密，确保只有服务器能够解密该密钥

## 常见HTTP状态码

- **1xx - 信息类（Informational）**
  - `100 Continue`: 表示服务器接收到请求的初始部分，并且客户端应继续发送剩余的请求
  - `101 Switching Protocols`：服务器同意切换协议，如升级到WebSocket
- **2xx - 成功（Successful）**

  - `200 OK`: 请求成功，服务器成功处理了请求

  - `201 Created`: 请求成功并在服务器上创建了新的资源

  - `202 Accepted`：请求已接受，但处理未完成

  - `204 No Content`: 请求成功，但服务器没有返回响应主体内容

- **3xx - 重定向（Redirection）**

  - `301 Moved Permanently`: 请求的资源已永久移动到新位置

  - `302 Found`: 请求的资源暂时移动到新位置

  - `304 Not Modified`: 客户端使用缓存的副本，资源未修改（协商缓存）

- **4xx - 客户端错误（Client Error）**

  - `400 Bad Request`: 请求无效，服务器无法理解

  - `401 Unauthorized`: 请求要求身份验证

  - `403 Forbidden`: 服务器拒绝请求，没有权限访问

  - `404 Not Found`: 请求的资源不存在

  - `405 Method Not Allowed`：请求方法不被允许

- **5xx - 服务器错误（Server Error）**

  - `500 Internal Server Error`: 服务器遇到意外错误

  - `501 Not Implemented`：服务器不支持请求功能

  - `502 Bad Gateway`: 服务器作为网关或代理收到无效响应

  - `503 Service Unavailable`: 服务器当前无法处理请求，一般用于临时维护或过载状态

  - `504 Gateway Timeout`: 服务器作为网关或代理无法及时响应

## HTTP缓存是什么

HTTP 缓存主要有两种类型：强缓存（Freshness Cache）和协商缓存（Validation Cache）。这些缓存机制是由服务器通过 HTTP 响应头来控制的。

1. 强缓存（Freshness Cache）：
   - 强缓存是利用响应头中的 `Cache-Control` 和 `Expires` 字段来实现的
   - `Cache-Control` 字段用于定义缓存策略，常见的值包括：
     - `no-store`：禁用缓存，每次都向服务器请求资源。
     - `no-cache`：缓存资源，但在每次请求时都验证资源是否过期。
     - `public`：允许缓存资源，并可被多个用户共享。
     - `private`：只允许单个用户缓存资源。
     - `max-age`：定义资源的最大缓存时间（单位为秒）。
   - `Expires` 字段指定资源的过期日期时间，由服务器返回一个绝对时间戳
   - 如果缓存仍然有效，浏览器会直接从缓存中获取资源，而不发送请求到服务器
2. 协商缓存（Validation Cache）：
   - 协商缓存是利用响应头中的 `Last-Modified` 和 `ETag` 字段来实现的
   - `Last-Modified` 字段表示服务器上资源的最后修改时间
   - `ETag` 字段是服务器为资源生成的唯一标识符（通常是哈希值）
   - 当浏览器发起请求时，会发送 `If-Modified-Since` 和 `If-None-Match` 等条件请求头到服务器，以验证资源是否过期
   - 如果资源未修改，服务器会返回 `304 Not Modified` 状态码，浏览器会从缓存中获取资源
   - 如果资源已修改，服务器会返回新的资源，并更新缓存中的副本

需要注意的是，强缓存和协商缓存可以一起使用，浏览器会根据缓存策略和服务器返回的响应头来判断是否使用缓存。开发者可以通过设置相应的响应头来控制缓存行为，从而提高网页加载性能和用户体验。

同时存在时，强缓存的优先级高于协商缓存。当资源命中强缓存时，浏览器不会发送请求到服务器，直接从缓存中获取资源。只有在资源未命中强缓存时，浏览器才会发送请求并使用协商缓存机制进行验证和决策。

## 浏览器缓存方式及优先级

浏览器缓存的优先级从高到低如下：

1. **Service Worker 缓存**：
   - Service Worker 可以完全控制缓存行为，优先级最高。
   - 如果 Service Worker 拦截了请求并返回缓存资源，浏览器不会触发其他缓存机制。
2. **Memory Cache**：
   - 对于当前页面已经加载的资源，浏览器会优先从内存缓存中读取。
3. **Disk Cache**：
   - 如果内存缓存中没有找到资源，浏览器会尝试从磁盘缓存中读取。
4. **强缓存**：
   - 如果资源在强缓存有效期内，浏览器会直接从缓存中读取资源，而不会向服务器发送请求。
5. **协商缓存**：
   - 如果强缓存失效，浏览器会向服务器发送请求，服务器通过 `Last-Modified` 或 `ETag` 判断资源是否更新。

在实际开发中，可以根据资源类型选择合适的缓存策略：

- **静态资源（如 JS、CSS、图片）**：
  - 使用强缓存（`Cache-Control: max-age=31536000`），并配合文件哈希或版本号实现缓存更新。
- **动态资源（如 API 数据）**：
  - 使用协商缓存（`Cache-Control: no-cache`），确保每次请求都向服务器验证资源是否更新。
- **离线应用**：
  - 使用 Service Worker 缓存，提供离线访问能力。

| 缓存方式       | 优先级 | 特点                                                             |
| :------------- | :----- | :--------------------------------------------------------------- |
| Service Worker | 最高   | 完全控制缓存行为，适合离线应用。                                 |
| Memory Cache   | 高     | 读取速度快，但缓存时间短。                                       |
| Disk Cache     | 中     | 读取速度较慢，但缓存时间长。                                     |
| 强缓存         | 中     | 通过 `Cache-Control` 和 `Expires` 实现，缓存有效期内不发送请求。 |
| 协商缓存       | 低     | 强缓存失效后，通过 `Last-Modified` 或 `ETag` 验证资源是否更新。  |

## HTTP2

1. 二进制协议：HTTP/2 使用二进制格式传输数据，而不是 HTTP/1.1 的文本格式。二进制协议更高效，解析速度更快，且减少了错误处理的复杂性。
2. 多路复用：HTTP/2 允许在同一个 TCP 连接上同时发送多个请求和响应（多路复用）。解决了 HTTP/1.1 的队头阻塞（Head-of-Line Blocking）问题，避免了因单个请求阻塞而影响其他请求的情况。
3. 头部压缩：HTTP/2 使用 **HPACK** 算法对 HTTP 头部进行压缩，减少了重复头部字段的传输。显著降低了头部数据的体积，提升了传输效率。
4. 服务器推送：允许服务器主动向客户端推送资源，而无需客户端明确请求
5. 流优先级：支持为每个请求设置优先级，确保重要的资源（如 CSS、JavaScript）优先传输。客户端可以动态调整流的优先级，优化页面加载性能。
6. 单一连接：使用单一 TCP 连接处理所有请求和响应，减少了建立和关闭连接的开销。避免了 HTTP/1.1 中因多个连接导致的性能问题。
7. 局限：依赖于 TCP 协议，仍然可能受到 TCP 队头阻塞的影响。在丢包率较高的网络环境下，性能可能下降。

<br />

## HTTP3

1. 基于QUIC协议：使用 **QUIC** 作为底层传输协议，而不是 TCP。QUIC 基于 **UDP**，具有更低的延迟和更好的性能。
2. 解决TCP队头阻塞：HTTP/2 虽然解决了应用层的队头阻塞，但仍然受限于 TCP 的队头阻塞（即一个丢包会影响整个连接）。HTTP/3 使用 QUIC 的独立流（Streams）机制，即使某个流丢包，也不会影响其他流的数据传输。
3. 更快的连接建立：QUIC 集成了 **TLS 1.3**，在建立连接时同时完成加密握手，减少了握手延迟。对于之前连接过的服务器，QUIC 支持 **0-RTT**（零往返时间）连接，进一步加快连接速度。
4. 改进的多路复用：每个流都是独立的，丢包不会影响其他流的数据传输。
5. 头部压缩：HTTP/3 使用 **QPACK** 算法对 HTTP 头部进行压缩，进一步减少头部数据的体积。QPACK 是 HPACK（HTTP/2 的头部压缩算法）的改进版本，适应了 QUIC 的流式传输特性。
6. 局限：需要服务器和客户端同时支持 QUIC 协议。在某些网络环境下，UDP 可能会被防火墙或中间设备限制。

## 常见的请求方法有哪些

1. GET：
   - GET 方法用于从服务器获取资源。
   - 通过在 URL 中传递参数，可以向服务器发送请求并获取响应的数据。
   - GET 请求是幂等的，即多次重复请求会产生相同的结果，不会对服务器产生副作用。
2. POST：
   - POST 方法用于向服务器提交数据，通常用于创建新的资源或执行某种操作。
   - 通过请求体（Request Body）传递数据给服务器。
   - POST 请求不是幂等的，即多次重复请求可能会对服务器产生不同的结果。
3. PUT：
   - PUT 方法用于向服务器更新（替换）指定的资源。
   - 客户端向服务器发送一个包含完整资源表示的请求，用于更新服务器上的资源。
4. DELETE：
   - DELETE 方法用于从服务器删除指定的资源。
   - 客户端向服务器发送一个请求，用于删除服务器上的资源。
5. PATCH：
   - PATCH 方法用于部分更新服务器上的资源。
   - 客户端向服务器发送一个包含要修改的资源部分内容的请求，用于更新服务器上的资源的部分信息。
6. HEAD：
   - HEAD 方法类似于 GET 方法，但不返回实际的响应主体。
   - 客户端发送 HEAD 请求，服务器返回响应头信息，用于获取资源的元数据。
7. OPTIONS：
   - OPTIONS 方法用于请求服务器支持的通信选项。
   - 客户端发送 OPTIONS 请求，服务器返回服务器支持的请求方法、头部信息等。
8. TRACE：
   - TRACE 方法用于对客户端到服务器之间的通信进行追踪。
   - 客户端发送 TRACE 请求，服务器返回请求信息，用于诊断和调试。

## GET和POST的区别

"GET" 和 "POST" 是两种常见的 HTTP 请求方法，用于在客户端和服务器之间传递数据。它们在使用场景和特点上有以下区别：

1. 数据传递方式：
   - GET：通过 URL 参数传递数据。数据附加在 URL 的末尾，以 "?" 开头，多个参数之间使用 "&" 分隔。
   - POST：通过请求体传递数据。数据放在请求体中，不会暴露在 URL 中。
2. 数据传输大小：
   - GET：由于数据附加在 URL 中，对传输的数据大小有限制，因为不同浏览器和服务器对 URL 的长度有限制，一般在几千个字符左右。GET 请求只能传递 ASCII 数据(字母、数字、英文符号，浏览器规定请求行和请求头只能包含 ASCII 字符，node环境则不需要)，遇到非 ASCII 数据需要编码
   - POST：由于数据放在请求体中，对传输的数据大小理论上没有限制，但实际上服务器和应用可能会有其自身的配置限制。
3. 安全性：
   - GET：由于数据在 URL 中可见，所以不适合传递敏感信息，例如密码等。因为浏览器历史记录、服务器日志等都可能记录 URL。
   - POST：相对于 GET，POST 提供了更好的安全性，因为数据不会直接显示在 URL 中，更适合传递敏感信息。
4. 幂等性：
   - GET：一般情况下是幂等的，多次请求同一个 URL 通常不会产生副作用。
   - POST：不是幂等的，多次请求同一个 URL 可能会产生不同的结果或副作用，例如插入数据库记录等。
5. 缓存：
   - GET：可以被缓存，浏览器和代理服务器会缓存 GET 请求的响应结果，以优化性能。
   - POST：默认情况下不会被缓存，因为 POST 请求可能产生不同的结果，对于相同的请求，通常要重新向服务器请求数据。
6. 使用场景：
   - GET：适合用于获取数据，例如查看网页、搜索等。
   - POST：适合用于提交数据，例如表单提交、上传文件等
7. 页面刷新：
   - GET：不会提示，但是可以保存为浏览器书签
   - POST：当前页面是通过 POST 请求得到的，则浏览器会提示用户是否重新提交，不可以保存为浏览器书签

总的来说，GET 和 POST 有不同的用途和特点。GET 更适合用于获取数据，且对于安全性和数据大小有一定限制；POST 更适合用于提交数据，且在安全性和数据传输大小方面相对较优。在实际应用中，根据具体的需求和场景选择合适的请求方法是很重要的。

## JWT是什么

JWT（JSON Web Token）是一种开放标准（RFC 7519），用于在网络间传输的 JSON 对象，通常用于身份验证和授权。

JWT 主要由三部分组成：

1. Header（头部）：包含了使用的算法和令牌类型等信息，以 Base64 编码形式表示
2. Payload（负载）：包含了要传输的数据，如用户身份信息、权限等，以 Base64 编码形式表示
3. Signature（签名）：由使用指定算法对 Header 和 Payload 进行签名后的字符串，用于验证令牌的完整性和真实性

JWT 的工作流程如下：

1. 用户通过提供有效的凭证（如用户名和密码）进行身份验证
2. 服务器验证凭证，并生成一个 JWT
3. 服务器将 JWT 发送回客户端，客户端将其保存在本地（通常是在浏览器的 Cookie 或本地存储中）
4. 客户端在后续请求中将 JWT 作为身份验证凭据发送到服务器
5. 服务器验证 JWT 的签名，并解析其中的数据来验证用户的身份和权限
6. 如果 JWT 验证通过，服务器允许对请求进行相应的操作

## 常见的安全策略

1. OAuth（开放授权）：OAuth 是一种授权机制，允许应用程序代表用户向第三方应用程序获取有限的访问权限。通过 OAuth，用户可以授权应用程序访问其受保护的资源，而无需直接共享其凭证（如用户名和密码）。这种机制广泛应用于第三方登录和 API 访问授权场景。

1. HTTPS（HTTP 安全）：HTTPS 是一种通过使用 SSL/TLS 加密来保护 HTTP 通信的协议。通过使用 HTTPS，可以确保在客户端和服务器之间传输的数据是加密的，并且提供身份验证和数据完整性，防止数据被窃听、篡改和伪造。
1. CORS（跨源资源共享）：CORS 是一种机制，用于控制跨域请求的访问权限。通过在服务端设置响应头部，可以限制跨域请求的访问范围，防止恶意网站利用用户的身份在其他域上执行恶意操作。
1. CSRF（跨站请求伪造）防护：CSRF 是一种攻击方式，攻击者借助用户的身份在用户不知情的情况下执行操作。为了防御 CSRF 攻击，可以使用随机生成的令牌（CSRF Token）对请求进行验证，确保请求来源于可信任的站点。
1. 输入验证和数据过滤：输入验证是一种在接收到用户输入之前对其进行验证和过滤的措施。通过使用验证库或正则表达式，可以防止输入的恶意数据进入应用程序，从而预防常见的安全漏洞，如 XSS（跨站脚本攻击）和 SQL 注入。
1. 安全审计和日志记录：记录和监控应用程序的行为并记录安全事件是保护应用程序安全的重要步骤。通过记录关键操作、异常事件和安全事件，可以及时发现和响应潜在的安全问题，并提供可追踪性和审计凭据。
1. CSP（内容安全策略）是一种通过定义可信任的内容源和限制加载内容的机制，用于防止跨站脚本攻击（XSS）等安全漏洞。通过 CSP，网站管理员可以通过指令控制浏览器的行为，限制加载和执行非信任来源的内容。它可以帮助增强网站的安全性，并减少恶意注入的风险。

这些安全策略通常可以结合使用，根据应用程序的需求和复杂性来选择合适的安全措施。重要的是采用多层次的防御机制，综合考虑不同的安全风险和威胁，以保护应用程序和用户的安全。

## 常见的网络安全问题

前端常见的网络安全问题主要包括以下几种：

1. 跨站脚本攻击 (XSS)：
   攻击者将恶意脚本注入到网页中，当其他用户访问该网页时，脚本会在用户浏览器中执行，从而盗取用户信息或进行其他恶意操作。

   解决方案：使用合适的编码和转义，对用户输入进行过滤和验证，不信任任何来自用户的数据，并使用 `Content Security Policy (CSP)` 来限制脚本的来源。

2. 跨站请求伪造 (CSRF)：
   攻击者通过伪造请求，利用用户已登录的身份在目标网站上执行操作，例如发表评论、转账等。

   解决方案：使用 CSRF Token 来验证请求的合法性，确保请求来自合法的来源，且包含用户的认证信息。

3. 跨站点注入攻击：
   包括 SQL 注入和 NoSQL 注入，攻击者通过向服务器发送恶意的数据库查询来获取未授权的数据或篡改数据。

   解决方案：使用参数化查询或 ORM 框架，避免直接拼接用户输入到查询语句中。

4. 敏感数据泄露：
   在前端代码中暴露敏感信息，使得攻击者可以轻易地获取到这些信息。

   解决方案：避免在前端代码中存储敏感数据，尽量将敏感信息存储在后端或使用安全的存储方式，同时使用 HTTPS 加密传输数据。

5. 不安全的第三方库：
   使用不安全或过时的第三方库可能存在漏洞，使得攻击者可以利用这些漏洞攻击网站。

   解决方案：定期更新第三方库到最新版本，仔细审查和评估第三方库的安全性和可信度。

6. 密码安全问题：
   存储用户密码不当或使用弱密码，使得攻击者可以轻易地破解用户密码。

   解决方案：使用加密算法对用户密码进行加密，加盐存储密码，并鼓励用户使用强密码。

7. 不安全的身份认证和授权：
   不正确地实现身份认证和授权机制，导致用户未经授权就能访问敏感资源。

   解决方案：使用安全的身份认证和授权机制，例如 OAuth、JWT 等。

8. 点击劫持：
   攻击者通过将恶意网页透明覆盖在用户点击的位置上，使得用户在不知情的情况下点击了恶意链接。

   解决方案：使用 X-Frame-Options 头部或 Content Security Policy (CSP) 来防止网页被嵌套在其他网页中。

综合来说，前端安全问题需要从多个方面来进行保护，包括对用户输入的处理、数据传输的加密、身份认证和授权的实现等。同时，及时更新和审查第三方库也是保障前端安全的重要措施。

## 进程和线程的区别

1. 定义：
   - 进程：进程是程序的执行实例。它是操作系统进行资源分配和调度的基本单位，包含了程序代码、数据和执行状态等信息。
   - 线程：线程是进程内的执行单元。一个进程可以拥有多个线程，它们共享进程的资源，但具有独立的执行路径和部分执行状态。
2. 资源占用：
   - 进程：每个进程都有独立的内存空间、文件句柄、设备和系统资源。它们之间的通信需要通过进程间通信（IPC）的方式。
   - 线程：线程共享所属进程的内存空间和资源，包括代码、数据和打开的文件等。线程间通信相对容易，因为它们可以直接读写共享内存。
3. 切换开销：
   - 进程：由于进程之间拥有独立的内存空间和资源，进程切换需要保存和恢复大量的上下文信息，包括寄存器、内存映像等，开销较大。
   - 线程：线程切换只需要保存和恢复少量的上下文信息，如寄存器状态，开销较小。
4. 并发性和并行性：
   - 进程：进程是操作系统进行资源分配和调度的基本单位。多个进程可以并发执行，通过操作系统的调度策略分时执行在单个或多个处理器上，实现并行性。
   - 线程：线程是进程内的执行单元，同一进程内的多个线程可以并发执行。多线程可以利用多核处理器实现真正的并行性。
5. 安全性：
   - 进程：由于进程间拥有独立的内存空间，进程间的错误不会互相影响，相对较安全。但进程间通信需要通过特定的机制来保证数据的一致性和同步性。
   - 线程：线程共享进程的内存空间，因此一个线程的错误可能会导致整个进程崩溃。线程之间的共享数据需要进行适当的同步操作来避免竞态条件等问题。

## 浏览器有哪些进程和线程

**浏览器是一个多进程多线程的应用程序**。

最主要的进程有：

1. 浏览器进程

   主要负责界面显示、用户交互、子进程管理等。浏览器进程内部会启动多个线程处理不同的任务。

2. 网络进程

   负责加载网络资源。网络进程内部会启动多个线程来处理不同的网络任务。

3. **渲染进程**

   渲染进程启动后，会开启一个**渲染主线程**，主线程负责执行 HTML、CSS、JS 代码。

   默认情况下，浏览器会为每个标签页开启一个新的渲染进程，以保证不同的标签页之间不相互影响。

## 渲染主线程是如何工作的

任务包括但不限于：

- HTML 解析：
  - 渲染主线程从网络接收到 HTML 文件后，会将其解析为 DOM（文档对象模型）树。
  - 解析过程中，渲染主线程会构建 DOM 树的结构，并将 HTML 标记转换为 DOM 元素。
- CSS 解析和计算样式：
  - 渲染主线程会解析 CSS 样式表，并计算每个元素的最终样式。
  - 样式计算涉及到 CSS 属性的继承、层叠和优先级等规则。
- 布局（Layout）：
  - 在布局阶段，渲染主线程确定每个元素在视口中的准确位置和大小。
  - 布局计算会考虑元素的尺寸、位置、边距和内边距等属性。
- 绘制（Painting）：
  - 绘制阶段是将布局后的元素绘制到屏幕上。
  - 渲染主线程根据布局信息和元素样式，使用图形库进行绘制操作，生成位图（Bitmap）。
- 栅格化（Rasterization）：
  - 栅格化是将绘制得到的位图转换为屏幕上的像素点。
  - 渲染主线程将位图分割成小的栅格，将每个栅格转换为屏幕上的像素。
- 合成和显示：
  - 最后，渲染主线程将栅格化后的像素传递给合成器（Compositor）进行合成。
  - 合成器负责将多个图层（Layer）组合成最终的屏幕显示结果。
- 每秒把页面画 60 次
- 执行全局 JS 代码
- 执行事件处理函数
- 执行计时器的回调函数

## 浏览器是如何渲染页面的

1. 当浏览器的网络线程收到 HTML 文档后，会产生一个渲染任务，并将其传递给渲染主线程的消息队列。在事件循环机制的作用下，渲染主线程取出消息队列中的渲染任务，开启渲染流程。
2. 整个渲染流程分为多个阶段，分别是： HTML 解析、样式计算、布局、分层、绘制、分块、光栅化、画。每个阶段都有明确的输入输出，上一个阶段的输出会成为下一个阶段的输入。这样，整个渲染流程就形成了一套组织严密的生产流水线。
3. 渲染的第一步是**解析 HTML**。解析过程中遇到 CSS 解析 CSS，遇到 JS 执行 JS。为了提高解析效率，浏览器在开始解析前，会启动一个预解析的线程，率先下载 HTML 中的外部 CSS 文件和 外部的 JS 文件。
4. 如果主线程解析到`link`位置，此时外部的 CSS 文件还没有下载解析好，主线程不会等待，继续解析后续的 HTML。这是因为下载和解析 CSS 的工作是在预解析线程中进行的。这就是 CSS 不会阻塞 HTML 解析的根本原因。
5. 如果主线程解析到`script`位置，会停止解析 HTML，转而等待 JS 文件下载好，并将全局代码解析执行完成后，才能继续解析 HTML。这是因为 JS 代码的执行过程可能会修改当前的 DOM 树，所以 DOM 树的生成必须暂停。这就是 JS 会阻塞 HTML 解析的根本原因。
6. 第一步完成后，会得到 DOM 树和 CSSOM 树，浏览器的默认样式、内部样式、外部样式、行内样式均会包含在 CSSOM 树中。
7. 渲染的下一步是**样式计算**。主线程会遍历得到的 DOM 树，依次为树中的每个节点计算出它最终的样式，称之为 Computed Style。在这一过程中，很多预设值会变成绝对值，比如`red`会变成`rgb(255,0,0)`；相对单位会变成绝对单位，比如`em`会变成`px`。这一步完成后，会得到一棵带有样式的 DOM 树。
8. 接下来是**布局**，布局完成后会得到布局树。布局阶段会依次遍历 DOM 树的每一个节点，计算每个节点的几何信息。例如节点的宽高、相对包含块的位置。大部分时候，DOM 树和布局树并非一一对应。比如`display:none`的节点没有几何信息，因此不会生成到布局树；又比如使用了伪元素选择器，虽然 DOM 树中不存在这些伪元素节点，但它们拥有几何信息，所以会生成到布局树中。还有匿名行盒、匿名块盒等等都会导致 DOM 树和布局树无法一一对应。
9. 下一步是**分层**主线程会使用一套复杂的策略对整个布局树中进行分层。分层的好处在于，将来某一个层改变后，仅会对该层进行后续处理，从而提升效率。滚动条、堆叠上下文、transform、opacity 等样式都会或多或少的影响分层结果，也可以通过`will-change`属性更大程度的影响分层结果。
10. 再下一步是**绘制**主线程会为每个层单独产生绘制指令集，用于描述这一层的内容该如何画出来。完成绘制后，主线程将每个图层的绘制信息提交给合成线程，剩余工作将由合成线程完成。
11. 合成线程首先对每个图层进行分块，将其划分为更多的小区域。它会从线程池中拿取多个线程来完成分块工作。
12. 分块完成后，进入**光栅化**阶段。合成线程会将块信息交给 GPU 进程，以极高的速度完成光栅化。GPU 进程会开启多个线程来完成光栅化，并且优先处理靠近视口区域的块。光栅化的结果，就是一块一块的位图
13. 最后一个阶段就是**画**了合成线程拿到每个层、每个块的位图后，生成一个个「指引（quad）」信息。指引会标识出每个位图应该画到屏幕的哪个位置，以及会考虑到旋转、缩放等变形。变形发生在合成线程，与渲染主线程无关，这就是`transform`效率高的本质原因。
14. 合成线程会把 quad 提交给 GPU 进程，由 GPU 进程产生系统调用，提交给 GPU 硬件，完成最终的屏幕成像。

## 性能优化

1. 减少HTTP请求：

   - Queueing: 在请求队列中的时间
   - Stalled: 从TCP 连接建立完成，到真正可以传输数据之间的时间差，此时间包括代理协商时间
   - Proxy negotiation: 与代理服务器连接进行协商所花费的时间
   - DNS Lookup: 执行DNS查找所花费的时间，页面上的每个不同的域都需要进行DNS查找
   - Initial Connection / Connecting: 建立连接所花费的时间，包括TCP握手/重试和协商SSL
   - SSL: 完成SSL握手所花费的时间
   - Request sent: 发出网络请求所花费的时间，通常为一毫秒的时间
   - Waiting(TFFB): TFFB 是发出页面请求到接收到应答数据第一个字节的时间
   - Content Download: 接收响应数据所花费的时间

   **建议将多个小文件合并为一个大文件，从而减少 HTTP 请求次数**。

2. 使用HTTP2：

   - **解析速度快**：服务器解析 HTTP1.1 的请求时，必须不断地读入字节，直到遇到分隔符 CRLF 为止。而解析 HTTP2 的请求就不用这么麻烦，因为 HTTP2 是基于帧的协议，每个帧都有表示帧长度的字段

   - **多路复用**：HTTP1.1 如果要同时发起多个请求，就得建立多个 TCP 连接，因为一个 TCP 连接同时只能处理一个 HTTP1.1 的请求

     在 HTTP2 上，多个请求可以共用一个 TCP 连接，这称为多路复用。同一个请求和响应用一个流来表示，并有唯一的流 ID 来标识。多个请求和响应在 TCP 连接中可以乱序发送，到达目的地后再通过流 ID 重新组建

   - **首部压缩**：HTTP/2 在客户端和服务器端使用“首部表”来跟踪和存储之前发送的键－值对，对于相同的数据，不再通过每次请求和响应发送

   - **优先级**：HTTP2 可以对比较紧急的请求设置一个较高的优先级，服务器在收到这样的请求后，可以优先处理

   - **流量控制**：由于一个 TCP 连接流量带宽（根据客户端到服务器的网络带宽而定）是固定的，当有多个请求并发时，一个请求占的流量多，另一个请求占的流量就会少。流量控制可以对不同的流的流量进行精确控制

   - **服务器推送**：HTTP2 新增的一个强大的新功能，就是服务器可以对一个客户端请求发送多个响应。换句话说，除了对最初请求的响应外，服务器还可以额外向客户端推送资源，而无需客户端明确地请求。

     例如当浏览器请求一个网站时，除了返回 HTML 页面外，服务器还可以根据 HTML 页面中的资源的 URL，来提前推送资源。

  - 在 performance profiling 之后，将频繁变动的动画部分所属的dom元素标记为 will-change，独立构成一个图层

## 网络性能如何优化

1. 减少请求次数：
   - 合并和压缩资源：将多个小的 CSS、JavaScript 文件合并为一个，并对文件进行压缩，减少请求次数和文件大小
   - 图片懒加载：延迟加载页面中的图片，只有当图片出现在可视区域时再进行加载
   - 使用字体图标或 CSS Sprites：减少图像请求，将多个图标合并为一张图，通过 CSS 控制显示区域
   - 使用缓存：利用浏览器缓存机制，减少对服务器资源的请求
2. 压缩和优化资源：
   - 使用 Gzip 压缩：服务器端启用 Gzip 压缩技术，减小传输的文件大小
   - 使用图像压缩：对图片进行压缩，减小文件大小，同时保持可接受的视觉质量
   - 优化代码：通过消除不必要的空格、注释、重复代码等来减小文件大小
3. 使用缓存机制：
   - 设置适当的缓存头：通过设置合适的 Cache-Control、Expires 和 ETag 等响应头来控制资源的缓存行为
   - 利用浏览器缓存：将静态资源设置为长期缓存，减少重复的网络请求
   - 使用 CDN（Content Delivery Network）：将静态资源分发到全球各地的服务器节点，加速资源的传输和加载
4. 建立并行连接：
   - 使用域名分片（Domain Sharding）：将页面上的资源请求分布到多个域名下，增加浏览器与服务器并行请求的数量
   - 使用 HTTP/2：HTTP/2 支持多路复用，可以在同一连接上并行传输多个请求和响应
5. 优化网络请求：
   - 减小请求大小：通过压缩和优化资源来减小请求的大小，减少传输时间
   - 使用 CDN 加速：使用 CDN 来提供静态资源，将资源就近分发到用户，减少传输时间
   - 使用预加载和预渲染：提前加载和渲染关键资源，提高页面的加载速度和响应性能
6. 流量控制和负载均衡：
   - 使用合适的负载均衡策略：将请求分发到多个服务器上，避免单个服务器过载
   - 使用流量控制机制：根据网络状况和服务器负载等因素，进行请求的限制和调整，保证服务的稳定性和性能
